# 本地直发脚本设计

## 1. 目标

将后端 API 和后台管理系统当前依赖手工复制命令的发布流程，封装为可审计、可验证、可回滚的 Shell 脚本。

本方案只负责发布已经准备好的代码，不负责开发分支流转。脚本不会自动合并、提交、推送或修改业务代码，也不处理微信小程序发布。

## 2. 核心决策

- 测试环境和生产环境使用两个独立入口，避免环境参数串用。
- 测试环境固定发布两个仓库的 `test` 分支。
- 生产环境固定发布两个仓库的 `master` 分支。
- 发布范围通过数字菜单选择：后端、后台、后端和后台。
- 分支名称、环境名称和危险确认均不接受自由文本输入。
- 公共能力由内部脚本复用，入口脚本不共享环境配置。
- 容器失败自动回滚，数据库不随容器自动反向回滚。
- 生产数据库禁止执行 `prisma db push --accept-data-loss`。

## 3. 文件布局

脚本由后端仓库统一管理，因为后端发布包含数据库和运行环境校验，并负责协调相邻的后台仓库。

```text
intelligent-community-admin/
└── deploy/
    └── local-direct/
        ├── deploy-test.sh
        ├── deploy-production.sh
        ├── rollback-test.sh
        ├── rollback-production.sh
        ├── config/
        │   ├── test.conf
        │   └── production.conf
        └── lib/
            ├── common.sh
            ├── preflight.sh
            ├── database.sh
            ├── sync-source.sh
            ├── deploy-api.sh
            ├── deploy-web.sh
            ├── health-check.sh
            ├── release-record.sh
            └── rollback.sh
```

入口脚本只加载与自身同名的固定环境配置：

- `deploy-test.sh` 只能加载 `test.conf`。
- `deploy-production.sh` 只能加载 `production.conf`。
- 入口不提供 `--env` 参数，不允许运行时覆盖环境。

## 4. 人工控制项

### 4.1 主菜单

```text
1. 发布新版本
2. 查看当前版本
3. 回滚上一版本
0. 退出
```

### 4.2 发布范围

```text
1. 后端 API
2. 后台管理系统
3. 后端 API + 后台管理系统
0. 取消
```

### 4.3 确认节点

用户只通过数字选项确认以下操作：

1. 确认目标环境、固定分支、提交号和发布范围。
2. 存在普通数据库迁移时，确认是否继续。
3. 测试环境检测到删表、删字段或其他数据丢失风险时，执行第二次风险确认。
4. 生产环境发布前执行最终二次确认。
5. 手动回滚时确认目标容器版本。

任何无效输入、空输入或非菜单选项都不会继续发布。所有确认默认值均为取消。

## 5. 脚本自动执行项

### 5.1 本地预检

- 验证操作系统具备 Bash、Git、Node.js、npm、rsync、SSH、curl 和 sha256 工具。
- 验证后端与后台仓库路径真实存在。
- 验证两个仓库当前分支符合目标环境。
- 验证工作区没有已修改、未跟踪或暂存但未提交的文件。
- 验证本地提交与对应远程分支一致，不自动拉取或推送。
- 输出仓库、分支、短提交号、提交说明和提交时间。
- 根据发布范围执行完整测试、构建和代码检查。

### 5.2 服务器预检

- 验证 SSH 可连接。
- 验证 Docker 可用。
- 验证目标服务器目录、Docker 网络、环境文件和目标容器存在。
- 验证磁盘空间足够构建镜像和保存备份。
- 从环境文件和容器配置读取环境摘要，但不输出数据库密码、Token、Cookie 或密钥。
- 验证目标数据库名称、API 容器、Web 容器、端口、域名、COS 前缀均与固定配置一致。
- 测试环境发现生产数据库或生产 COS 前缀时立即终止。
- 生产环境发现测试数据库或测试 COS 前缀时立即终止。

### 5.3 数据库处理

- 只有发布范围包含后端时才检查数据库。
- 在任何数据库写入前生成带时间和提交号的压缩备份。
- 验证备份非空并生成 SHA-256 校验值。
- 检查 Prisma schema、migration 状态和目标数据库实际结构。
- 无数据库变更时跳过数据库写入。
- 测试环境允许在备份和风险确认后使用迁移镜像同步 schema。
- 生产环境只允许执行仓库中已提交的 Prisma migration。
- 生产环境检测到 migration 历史缺失、修改或漂移时终止发布。
- 数据库命令失败时停止发布，恢复旧 API 容器，不继续发布 Web。

### 5.4 源码同步与镜像

- 使用 `rsync` 从本地已验证工作区同步到服务器固定目录。
- 排除 `.git`、环境文件、`node_modules`、构建产物和系统临时文件。
- 镜像标签使用环境和 Git 短提交号，不只使用 `latest`。
- 后端分别构建迁移镜像和精简运行镜像。
- 后台镜像通过 `ADMIN_API_UPSTREAM` 固定连接同环境 API。
- 构建失败时保留当前运行容器，不进入切换阶段。

### 5.5 容器切换和健康检查

- 先停止并重命名当前容器为上一版本，不立即删除。
- 使用新镜像创建同名容器。
- 恢复原有端口、网络、网络别名、环境文件和重启策略。
- 后端健康检查必须通过环境对应的 `/api/health`。
- 后台健康检查同时验证首页和经 Web 代理访问的 `/api/health`。
- 校验后台 Nginx 实际 upstream 指向同环境 API。
- 校验 API 的 `APP_ENV`、数据库名和 COS 前缀。
- 健康检查失败时自动删除失败的新容器并恢复旧容器。
- 后端失败时不继续发布后台。

### 5.6 发布记录

每次发布生成本地和服务器两份记录，内容包括：

- 发布流水号和时间。
- 执行用户和目标环境。
- 发布范围。
- 两个仓库的分支和提交号。
- 镜像标签与镜像摘要。
- 数据库名称、迁移方式和备份路径。
- 新旧容器名称。
- 健康检查结果。
- 发布成功、失败或已回滚状态。

记录中不得包含密码、完整数据库连接串、JWT、微信凭证、COS 密钥或请求敏感参数。

## 6. 测试环境发布流程

```text
运行 deploy-test.sh
-> 菜单选择发布范围
-> 固定校验 test 分支
-> 本地测试和构建
-> 展示发布摘要并确认
-> 服务器环境隔离检查
-> 后端范围：备份 ic_test、检查数据库变更并确认
-> 同步源码并构建带提交号镜像
-> 切换后端并健康检查
-> 切换后台并验证其代理到测试 API
-> 写入发布记录
```

测试环境固定信息包括：

- API 容器：`ic-test-admin-api`
- Web 容器：`ic-test-admin-web`
- 数据库：`ic_test`
- API 端口：`3002 -> 3000`
- Web 端口：`3001 -> 80`
- API 网络别名：`api-test`
- COS 前缀：`test`
- 公共 API：`https://lllhjh.asia/test-api`

## 7. 生产环境发布流程

```text
运行 deploy-production.sh
-> 菜单选择发布范围
-> 固定校验 master 分支
-> 本地测试和构建
-> 展示生产发布摘要
-> 第一次确认
-> 服务器生产环境隔离检查
-> 后端范围：备份生产数据库并验证 migration
-> 第二次生产确认
-> 同步源码并构建带提交号镜像
-> 切换后端并健康检查
-> 切换后台并验证其代理到生产 API
-> 写入发布记录
```

生产脚本不得读取测试环境配置，也不得接受运行参数将目标改为测试容器或测试数据库。

## 8. 回滚设计

### 8.1 自动回滚

- 新镜像构建失败：不停止旧容器。
- 数据库命令失败：恢复旧 API 容器并停止流程。
- 新 API 健康检查失败：删除新 API 容器并恢复旧 API。
- 新 Web 健康检查失败：删除新 Web 容器并恢复旧 Web。
- API 和 Web 同时发布时，任何一个容器失败都恢复本次已经切换的全部容器，避免前后端版本不一致。
- 容器回滚不反向恢复数据库；数据库变更必须保持对上一版 API 的兼容性，否则发布前检查直接终止联合发布。

### 8.2 手动回滚

独立回滚入口只允许选择发布记录中已验证存在的上一版本：

- `rollback-test.sh` 只能操作测试容器。
- `rollback-production.sh` 只能操作生产容器。
- 回滚前显示当前版本、目标版本、发布时间和提交号。
- 回滚后执行与发布相同的健康检查并写入回滚记录。

数据库不会跟随容器自动回滚。需要恢复数据库时，必须单独评估备份之后产生的数据，并由专门流程执行恢复或前向修复 migration。

## 9. 错误处理

- 所有脚本启用严格模式，任何未处理错误都会终止当前阶段。
- 每个阶段返回明确的状态码和中文错误说明。
- 远程命令通过固定脚本输入执行，不拼接未经校验的用户文本。
- 临时目录由系统安全创建，并在退出时清理。
- 中断信号触发清理；若已进入容器切换阶段，则执行对应回滚函数。
- 日志输出按阶段编号，失败时给出可重新执行的安全入口，不输出危险的半截命令。

## 10. 验证方案

### 10.1 静态测试

- ShellCheck 通过。
- 所有脚本均能被 `bash -n` 解析。
- 测试配置不包含任何生产容器、数据库或 COS 前缀。
- 生产配置不包含任何测试容器、数据库或 COS 前缀。
- 入口脚本不能加载另一个环境的配置。

### 10.2 自动化行为测试

使用伪造命令目录替代 Git、SSH、Docker、rsync 和 curl，覆盖：

- 菜单取消和无效输入。
- 错误分支、脏工作区和远程未同步。
- SSH 不可用、磁盘不足和环境文件缺失。
- 环境数据库交叉连接。
- 数据库备份失败和校验失败。
- 普通迁移取消。
- 数据丢失风险取消。
- 生产环境拒绝 `db push --accept-data-loss`。
- 镜像构建失败时旧容器保持运行。
- API 或 Web 健康检查失败时自动回滚。
- 敏感配置不会进入终端和发布记录。

### 10.3 测试环境演练

正式启用生产脚本前，先在测试环境完成：

1. 后端单独发布。
2. 后台单独发布。
3. 后端和后台联合发布。
4. 人工制造健康检查失败并验证自动回滚。
5. 执行一次手动容器回滚。
6. 核对数据库备份可读取且校验值一致。

只有测试环境演练全部通过，生产入口才允许标记为可用。

## 11. 不包含的范围

- 不自动创建、合并或推送 Git 分支。
- 不发布微信小程序。
- 不配置 DNS、HTTPS 证书或云安全组。
- 不自动升级 npm、Prisma、Docker 或服务器系统依赖。
- 不自动恢复数据库备份。
- 不替代业务功能验收和小程序体验版验收。
