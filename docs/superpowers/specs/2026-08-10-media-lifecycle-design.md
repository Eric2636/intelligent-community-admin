# 媒体生命周期管理设计

## 目标

管理上传到腾讯云 COS 的业务媒体，防止用户未发布或删除业务数据后留下孤儿图片、视频。

## 范围

本期仅修改后端与数据库，不修改小程序界面和交互。覆盖：

- 小区留言及回复的图片、视频；
- 业主互助任务、任务完成凭证的图片、视频；
- 小区市场商品及评论的图片、视频；
- 用户头像审核图片。

意见反馈当前没有媒体字段，不在本期范围。小程序静态资源、默认头像和市场分类资源不属于业务上传媒体，永不由此机制删除。

## 数据模型

新增 `MediaAsset` 表，每个通过 `POST /api/upload/media` 上传的 COS 文件创建一条记录：

- `id`：媒体资产 ID；
- `objectKey`、`url`：COS 对象键和公开访问地址；
- `uploaderId`、`module`、`mediaType`：上传者、模块及图片/视频类型；
- `state`：`PENDING`（待关联）、`ATTACHED`（已关联）、`DELETE_PENDING`（待删除）、`DELETED`（已删除）、`DELETE_FAILED`（删除失败）；
- `createdAt`、`attachedAt`、`deleteRequestedAt`、`deletedAt`、`deleteAttempts`、`lastDeleteError`。

`objectKey` 为唯一键，`url` 保留为可展示的长文本；这样既能唯一标识同一 COS 对象，也不会因 MySQL 的 UTF-8 索引长度限制而无法迁移。只接受当前环境 COS 前缀下、由本服务记录的对象，避免对静态文件或其他环境对象做删除操作。

## 数据流

### 上传与发布

1. 小程序保持“选择即上传”。上传接口完成 COS 上传后写入 `PENDING` 资产记录，原响应 URL 保持不变。
2. 创建或更新业务内容时，后端从已验证的媒体 URL 找到属于当前用户的 `PENDING` 记录，和业务写入放入同一个数据库事务，将其置为 `ATTACHED`。
3. 未被发布内容关联的 `PENDING` 资产，在创建 24 小时后进入删除队列。

### 业务删除

删除小区留言、回复、市场商品、市场评论，或删除草稿/已撤销任务时：

1. 在数据库事务内读取对应媒体 URL；
2. 将相关 `ATTACHED` 资产置为 `DELETE_PENDING`；
3. 执行原有软删除或物理删除；
4. 事务提交后异步删除 COS 对象。

任务完成凭证只有在其所属任务被删除时才进入删除队列。媒体删除不阻塞用户的业务删除：COS 失败会保留 `DELETE_FAILED` 状态、错误信息和重试次数，供定时任务重试。

### 定时清理

后端启动一个低频后台任务（每 15 分钟）：

- 找出超过 24 小时的 `PENDING` 资产；
- 处理 `DELETE_PENDING` 与可重试的 `DELETE_FAILED` 资产；
- 调用 COS `deleteObject`；
- 成功后标记 `DELETED`，失败后记录错误并递增次数。

任务具备互斥锁，避免多实例重复处理同一批对象。实际删除前再次校验对象键匹配当前 `COS_ENV_PREFIX` 和受支持模块。

## 历史生产孤儿媒体

本次生产库已经清除测试数据，保留的清理前备份可作为一次性历史清理清单来源。实施后提供仅供运维执行的脚本：从该备份提取媒体 URL，去重、校验生产前缀后删除，并逐项输出成功、跳过和失败结果。该脚本不扫描或删除默认资源。

先在生产环境以 `npm run cleanup-legacy-media -- --backup <备份路径> --env production` 执行 dry-run；只有核对数量无误且获得明确授权后，才追加 `--confirm` 实际删除。

## 审计与可观测性

- 用户侧媒体删除不新增后台菜单；
- 后台管理员触发内容删除时，沿用现有操作审计；
- 定时任务和一次性运维脚本输出结构化结果日志；
- 不因为 COS 删除失败回滚已经成功的业务删除。

## 验收标准

1. 用户选择图片后不发布，24 小时后资产被删除。
2. 发布成功后，媒体资产为 `ATTACHED`，不会被临时清理。
3. 用户删除自己的帖子、回复、商品、商品评论或可删除任务后，关联媒体进入删除队列并最终在 COS 删除。
4. COS 删除异常时，业务删除仍成功，资产可被后续任务重试。
5. 非当前环境、非受支持模块或未登记的 URL 不会被删除。
6. 小程序现有上传、发布和删除接口兼容，无需页面改动。
