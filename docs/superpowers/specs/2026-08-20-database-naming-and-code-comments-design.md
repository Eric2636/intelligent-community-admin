# 数据库命名规范与核心函数注释设计

## 1. 目标

本次改动优先统一管理 API 使用的 MySQL 物理表名，并检查现有字段命名。数据库命名调整完成后，为关键业务函数补充面向维护者的说明，使开发者能够快速理解函数职责、事务边界、权限条件、数据副作用和缓存行为。

本次首先修改并验证隔离的本地开发环境，不连接或修改测试、预发布、生产或其他远程数据库。

本次属于数据库物理命名重构，不允许改变任何业务功能。Prisma Model 名、Service 调用方式、API 路径、请求与响应结构、权限规则、状态机、缓存键、数据内容和用户可见行为必须保持不变。

## 2. 范围

### 2.1 表命名

Prisma Model 保持 PascalCase 单数，MySQL 物理表统一为 snake_case 复数。四张遗留表调整如下：

| Prisma Model | 当前物理表 | 目标物理表 |
| --- | --- | --- |
| `User` | `User` | `users` |
| `AdminUser` | `AdminUser` | `admin_users` |
| `Task` | `Task` | `tasks` |
| `AppSettingTab` | `AppSettingTab` | `app_setting_tabs` |

Schema 通过 `@@map(...)` 维持稳定的 Prisma Model API，业务代码继续使用 `prisma.user`、`prisma.adminUser`、`prisma.task` 和 `prisma.appSettingTab`。

### 2.2 字段命名

现有物理字段继续使用 camelCase，例如 `userId`、`createdAt` 和 `deletedAt`。本阶段不批量重命名字段，原因是字段同时影响 Prisma、原生 SQL、接口契约、历史数据和部署回滚，风险显著高于表名统一。

本次检查并记录以下后续事项，但不在当前迁移中处理：

- `desc` 应在独立接口兼容方案中评估改为 `description`。
- `birth` 的主要问题是数据类型而非命名，应评估迁移为日期类型。
- `price`、`reward` 等金额或报酬字段应根据业务计算需求评估 Decimal。
- `status`、`type`、`identityType` 等字段应优先使用明确的枚举类型。
- 历史兼容字段 `contact`、`images` 在旧客户端下线后通过独立迁移清理。

### 2.3 原生 SQL

所有运行时代码中的原生 SQL 必须使用迁移后的物理表名。重点修正：

- 用户行锁查询从 `User` 改为 `users`。
- 商城分类删除检查从错误的 `MallItem` 改为 `mall_items`。
- 搜索并消除运行时代码对 `User`、`AdminUser`、`Task`、`AppSettingTab`、`MallItem` 等旧物理表名的直接引用。

已经执行过的历史迁移不回写。历史迁移描述的是当时的数据库状态，修改历史文件会破坏迁移校验和并使已部署环境产生漂移。

## 3. 迁移设计

新增一个仅向前执行的 Prisma migration，使用 MySQL 单条原子 `RENAME TABLE`：

```sql
RENAME TABLE
  `User` TO `users`,
  `AdminUser` TO `admin_users`,
  `Task` TO `tasks`,
  `AppSettingTab` TO `app_setting_tabs`;
```

单条 `RENAME TABLE` 保证四张表要么全部成功，要么全部不生效，避免应用代码面对部分新名称、部分旧名称的中间状态。

迁移不删除数据，不修改列，不重建表。表上的主键、唯一索引、普通索引和外键随表重命名保留。

## 4. 本地数据库安全门槛

实际执行迁移前必须完成以下只读核验：

1. 从应用实际加载的配置确认 host、port 和 database name。
2. host 必须是 `127.0.0.1`、`localhost`、本机 Unix socket 或已确认的本地 Docker 容器。
3. 数据库名称必须是明确的本地开发库，不能是 `ic_test`、`ic_prod` 或其他共享库。
4. 确认应用进程与准备迁移的数据库目标一致。
5. 查询四张旧表存在、四张新表不存在。
6. 查询 Prisma migration 状态，确认没有失败或未解决的迁移记录。
7. 创建迁移前结构与行数快照；如果本地库包含不可重建数据，再创建可恢复备份。

任一条件无法证明时停止数据库写入，只保留代码和迁移文件。

## 5. 函数注释规范

注释覆盖业务入口、Service 公共方法、事务函数、权限判断、缓存失效和复杂并发逻辑，优先处理以下模块：

- `src/routes`：路由注册函数和非显然的认证、回调、上传入口。
- `src/modules/database`：数据库结构查询、备份设置、任务与租约。
- `src/modules/admin`：管理员权限、内容管理、审计和事务包装。
- `src/modules/forum`：发布、回复、报名、点赞、收藏、通知和缓存。
- `src/modules/task`：状态机、CAS 更新、通知和媒体生命周期。
- `src/modules/mall`：商品、分类、订单、评论和幂等操作。
- `src/middleware`：鉴权、错误处理、审计和访问日志。
- `src/lib`：数据库、缓存和并发相关的共享函数。

每条 JSDoc 根据需要说明：

- 函数承担的业务职责。
- 关键参数和返回值的业务含义。
- 使用的事务、行锁、唯一约束或 CAS 条件。
- 权限与调用前置条件。
- 会写入的主要数据和外部副作用。
- 成功提交后执行的缓存失效或异步动作。

不为简单 getter、直接字段映射、一行包装器和含义明显的局部函数添加重复注释。注释解释“为什么和有哪些约束”，不逐行翻译代码。

## 6. 测试设计

采用测试先行：

1. 新增数据库命名契约测试，断言四个 Prisma Model 映射到目标表名；在修改 Schema 前测试必须因缺少映射而失败。
2. 新增迁移契约测试，断言迁移使用一条 `RENAME TABLE` 同时重命名四张表。
3. 新增运行时原生 SQL 契约测试，禁止受影响源码继续引用旧物理表名，并覆盖商城分类错误表名。
4. 修改 Schema、迁移和原生 SQL，使新增测试通过。
5. 运行 `prisma validate`、TypeScript no-emit 检查和完整后端测试。
6. 运行 lint 并确认不新增错误；当前已有 lint 问题单独报告，不借本次命名迁移扩大修复范围。
7. 在安全门槛全部通过后，对隔离本地数据库执行 migration deploy，并核验新表存在、旧表不存在、关键表行数一致、应用查询正常。

### 6.1 无功能影响验收标准

只有同时满足以下条件，才可认定本地改动成功：

- 迁移前后四张表的行数一致。
- 迁移前后四张表的列、主键、唯一索引和普通索引除表名外保持一致。
- Prisma Client 能使用原有 Model API 完成四张表的代表性只读查询。
- 完整后端测试保持全部通过，不能通过修改既有业务断言来迁就命名改动。
- TypeScript no-emit 检查通过，Prisma Schema 校验通过。
- API 路径、DTO、响应结构和 OpenAPI 定义没有变化。
- 运行时代码不存在对四张旧物理表名的依赖。
- 本次迁移前后不新增、删除或更新任何业务数据行。

出现测试失败、结构不一致、行数不一致、应用查询失败或数据库目标不明确时，立即停止后续步骤。若表名已经变更，则先执行反向原子重命名恢复本地数据库，再排查原因。

## 7. 部署与回滚

本次不部署测试或生产环境。

本次也不修改 `test`、`master`、`main` 或任何发布分支，不执行推送、合并、上传或发布操作。所有代码、迁移和数据库验证仅保留在本地 `dev` 工作区与已确认的隔离本地数据库中。

未来发布时必须保证迁移先于新应用代码执行，因为新 Prisma Schema 和原生 SQL只识别新表名。发布前应备份数据库并记录四张表的行数与索引结构。

若本地验证需要回滚，使用一条反向的原子 `RENAME TABLE` 将四张表恢复为旧名称，并恢复与旧表名匹配的应用代码。生产回滚方案必须在正式发布计划中再次确认，不能临时修改已提交迁移。

## 8. 非目标

- 不修复缺失的全量初始基线迁移。
- 不重写或修改已执行的历史迁移。
- 不统一所有物理列为 snake_case。
- 不改变 API 请求或响应字段。
- 不调整金额、日期和状态字段的数据类型。
- 不在本次工作中重构所有大型 Service。
- 不连接或修改任何远程数据库。
